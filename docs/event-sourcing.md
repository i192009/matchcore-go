# Events and snapshots

An append-only `events` table records one envelope for each committed instrument command, including business rejection. Its primary ID is `instrument:sequence`. The envelope contains schema version 1, configuration version 1, instrument, contiguous command sequence, correlation key, explicit millisecond timestamp, changed orders with before/after values, execution records and semantic subevents. Sub-events include OrderAccepted, OrderRejected, OrderPartiallyFilled, OrderFilled, OrderCancelled, BalanceReserved, BalanceReleased, TradeExecuted and SettlementCompleted as applicable. A filled incoming order implies acceptance and its final state in a single atomic envelope; no observer sees an intermediate accepted-but-unsettled trade.

Sequences count committed **commands**, not individual fills. A multi-fill order has one sequence and stable trade IDs `instrument:sequence:trade-index`. `orders.sequence` records original acceptance priority; maker fills preserve it. `updated` records the command timestamp. Versioned command outcomes contain the exact original response for retries. Matching never reruns during replay: committed decisions are applied in sequence with before-state checks.

Authoritative payloads are stored as exact byte strings with SHA-256 checksums; JSONB projections are not the replay source. A trigger denies ordinary event UPDATE/DELETE. The application role in this local demo is intentionally simple; a database superuser can bypass triggers and is outside the integrity threat model. Production-grade role separation and signed archives would be separate work.

Snapshots store instrument configuration, all open orders in canonical price/FIFO order, sequence, schema version and checksum. The writer creates one every 100 committed commands and at safe graceful shutdown. Snapshot failure is logged; the complete event log is retained. A snapshot is an acceleration structure, not an alternate financial authority. Account balances, reservations and settlements are already transactional database state and are not financially re-applied during replay.

Recovery loads the newest snapshot, validates its checksum, schema and exact configuration, restores FIFO state, then checks and applies subsequent events. It requires contiguous sequences and agreement with the instrument sequence and open-order SQL projection. Corrupt snapshots and events fail readiness instead of being silently ignored. See [recovery procedures](recovery.md).

The outbox row is inserted beside every event. One publisher batch at a time holds a transaction advisory lock, publishes in instrument sequence order, waits for JetStream durable acknowledgements, and marks the outbox rows published. A crash after broker acknowledgement but before SQL commit repeats publication. Stable `Nats-Msg-Id` reduces duplicate broker storage inside a ten-minute window; clients must still deduplicate instrument sequences without relying on that window. Stream exhaustion rejects new publishes, leaving SQL events pending for retry.
