# Consistency and accounting

The transaction is the exchange's consistency boundary. An instrument writer first checks durable idempotency, then computes a read-only plan with recorded identities, sequence and timestamp. The SQL transaction locks the instrument row, checks owner epoch and expected sequence, locks participating account rows in sorted order, checks idempotency again, then locks balances in sorted order. Account existence, trading restriction, instrument limits, initial gross funding and duplicate client IDs are checked before any plan can commit.

Available and reserved balances are separate nonnegative integers. For each affected order, its `reserved` field in the transactional order projection is the reservation record. Settlement calculates total asset transfers and the difference between old and final reservation. It posts `available_delta = total_delta - reserved_delta`. Incoming gross funding is checked while the account lock is held, even if the net outcome would receive other proceeds. IOC reservations can net to zero within the same transaction; no transient balance is exposed.

All financial deltas are summed by asset and must balance to zero. Every trade debits buyer USD and seller base, credits seller USD and buyer base, and credits both quote fees to `fees`. The same transaction persists order changes, trades, settlements, balance changes, ledger entries, a checksummed authoritative event envelope, the command result, the instrument sequence and the outbox row. Database uniqueness enforces account/client-ID, account/idempotency-key, event sequence, trade-ID and settlement-ID invariants. User-specific order histories are projections of these commits.

Funding is an explicit **simulation issuance** operation. `SeedAccount` atomically creates all asset rows and increases the recorded `supply`. Existing accounts are left untouched, so repeated seeding cannot replenish spent funds. There are no deposits, withdrawals, transfers to real people or external payment integrations. Conservation tests compare all account totals, including fees, with issued supply.

Only after SQL commit does the writer apply the committed plan and publish a new immutable depth view. Pre-commit SQL failure leaves the book unchanged. An uncertain commit outcome or an apply/precondition failure marks the matcher unsafe, makes readiness fail, and stops command admission until restart and recovery. An HTTP deadline does not prove a command failed: retry its original key.

Each owner holds a dedicated PostgreSQL session advisory lock. Claiming increments the instrument's durable epoch; each financial transaction checks that epoch under the same row lock used for sequence advancement. A replacement owner cannot race a financial transaction past that check. Session health is probed each second; ownership loss is also detected on every commit. Read endpoints can briefly show an older committed view during a commit or connection-loss detection. They never show an uncommitted plan. The database read projections can be ahead of the book during the post-commit apply interval. Read-your-response holds after the actor applies a normal successful command.

The three books can plan independently, but an account trading shared USD coordinates through database locks. The central fee account is also a shared lock, so traded commits can contend even with distinct traders; partitioning fee collectors is future work. This intentionally favors simple balanced accounting over parallel commit throughput. The same account/key namespace spans place and cancel commands and all instruments. Key conflicts return 409/AlreadyExists. Order upserts also verify account/client/instrument identity so an ID collision cannot overwrite another aggregate. Business rejections are committed, replayable and idempotent. Unauthorized or malformed transport requests do not enter the event log.

There is no general automatic transaction retry. Unknown outcomes require recovery, and safe request retries must use durable idempotency. External messages are at least once. Settlement never happens in a NATS consumer.
