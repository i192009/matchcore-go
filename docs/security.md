# Security assumptions

This repository operates on simulated assets. Development credentials in `.env.example` are public examples. `.env` is ignored. No production secret is embedded in code, images or frontend assets. Authenticated identities come from environment-configured scoped API keys; account identity is never accepted from order input. The server stores a SHA-256 key lookup in memory and does not log keys. Configure unrelated, high-entropy keys for any shared environment.

Keys have trader/admin roles. Place, cancel, balance, audit, summary and own-execution operations use the authenticated account. Cancellation verifies ownership. The administrative restriction endpoint requires `admin`; a restriction blocks new orders while preserving the ability to cancel existing exposure. Scoped keys and fixed configured account identities avoid an unauthenticated user-registration surface. Seeding is a local operator command with database access.

HTTP bodies are bounded to 16 KiB and headers to 16 KiB; gRPC command messages are bounded to 16 KiB. Commands have ten-second server deadlines. Per-key token buckets allow 200 requests/s and a burst of 400 in each service process; these are local limits, not a global distributed quota. Instrument channels hold at most 1,024 commands; books allow 100,000 resting orders and commands at most 1,024 executions. WebSocket clients have five seconds to authenticate, 4 KiB inbound messages, 128-message output/synchronization buffers, five-second write deadlines and a 1,000-client gateway admission limit.

The WebSocket gateway checks exact Origin against `ALLOWED_ORIGINS`, authenticates in the first message rather than a URL query, and rejects requests for another account's private events. Public trade data excludes counterpart identities. Snapshot and delta sequencing detect missed messages; slow clients are disconnected. HTTP CORS uses explicit origins. Frontend assets use a restrictive CSP and no external scripts or fonts. Session storage keeps the demo key only in the current browser session; sign-out clears it.

All SQL values are parameterized. Fixed table/schema identifiers in the test harness are generated internally. Go financial arithmetic uses checked integer products and conservative fee reservations; SQL enforces nonnegative balances and uniqueness. Asset conservation and balanced ledger postings are tested.

Containers run as non-root application users. Host ports bind loopback. The Compose network uses plaintext gRPC, PostgreSQL, Redis, NATS and HTTP for local development. TLS termination, mTLS, database role separation, secret rotation, distributed rate limiting, audit retention, encrypted backups and broker credentials are required deployment work before exposing a shared system. Metrics and health interfaces assume the trusted local network; they are not public authenticated customer endpoints.

Go dependency checks and npm audit run in CI. Current scan artifacts live in `benchmarks/results/`. Tool results are dated observations, not a future vulnerability guarantee. Container image references use maintained vendor versions; patch them regularly. No regulatory, asset-custody or production-compliance claim is made.
